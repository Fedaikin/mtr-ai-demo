# Демонстрация анализа МТР за 7–10 минут

За один короткий проход вы увидите канонические данные 24/30, выполните полный серверный сценарий, откроете отчёт с golden-распределением и получите grounded-ответ от «МТР-аналитика». Grounded означает, что факты ответа подтверждены вызовами инструментов и ссылками на конкретные источники.

> Все сущности и нормативные правила в этом руководстве синтетические. Не загружайте реальные спецификации, контакты или закрытые документы.

## Что понадобится

- Node.js `24.x`;
- pnpm `11.16.0`;
- установленные зависимости: `pnpm install --frozen-lockfile`;
- свободный порт `3000`;
- браузер.

Подробная первичная настройка приведена в [эксплуатационной инструкции](operations.md#как-запустить-прототип-локально).

## Маршрут демонстрации

| Этап | Ориентир |
|---|---:|
| Запуск и проверка данных | 2 мин |
| Полный сценарий | 2 мин |
| Отчёт и экспорт | 2 мин |
| МТР-аналитик и аудит | 2–4 мин |

## Шаг 1. Запустите чистый demo-контур

Из каталога `mtr-prototype` выполните:

```bash
test -e .env.local || cp .env.example .env.local
node --env-file=.env.local --import tsx scripts/migrate.ts
node --env-file=.env.local --import tsx scripts/seed.ts
pnpm dev
```

`db:seed` удаляет прежние запуски, диалоги и другие строки только доверенного demo-пользователя, затем восстанавливает канонический набор. Не выполняйте эту команду, если текущую локальную demo-историю нужно сохранить.

Откройте [http://localhost:3000](http://localhost:3000). Приложение перенаправит на `/login`; используйте приватно выданные синтетические реквизиты. Экран входа намеренно их не показывает. После входа на экране «Обзор анализа МТР» должны быть видны:

- пользователь `Демо-пользователь 1`;
- `3 584` актуальные позиции;
- `83` спецификации Appius;
- состояния интеграций **Доступна**.

Точные счётчики SAP проверяются readiness-ответом `GET /api/health?check=ready`: `sapMaterials=30` и `sapBalances=30`.

Это первый рабочий результат: приложение уже читает мигрированную БД и фильтрует данные по доверенной серверной сессии.

## Шаг 2. Посмотрите актуальную версию Appius

1. Откройте раздел **Спецификации**.
2. Выберите «Трубопроводный узел — базовая спецификация».
3. Проверьте метку `Версия 3 · актуальная для анализа` и восемь позиций.
4. Откройте историю версий. Исторические записи доступны для просмотра, но новый анализ использует только актуальную версию.

Контрольный идентификатор этой спецификации: `spec-demo-piping-001`; актуальная версия: `spec-demo-piping-001-v3`.

## Шаг 3. Выполните полный анализ

1. Откройте **Администрирование → Моделирование** или адрес [http://localhost:3000/admin/scenarios](http://localhost:3000/admin/scenarios).
2. В поле **Сценарий** выберите **Полный анализ спецификации**.
3. В поле **Спецификация** оставьте **Эталонный набор · 24 позиции**. Остальные 80 спецификаций доступны для отдельного запуска.
4. В поле **Режим** оставьте **Обычный**.
5. Нажмите **Запустить сценарий**.

POST-запрос только создаёт запись запуска, после чего серверный bounded runner сам выполняет атомарные шаги и сохраняет прогресс. Браузер лишь опрашивает `GET` и может быть закрыт: выполнение не зависит от открытой вкладки. Через несколько секунд статус станет **Завершён**.

В журнале должны быть шесть завершённых шагов:

1. загрузка актуальной версии Appius;
2. синхронизация снимка SAP;
3. распределение ответственности;
4. поиск складских совпадений;
5. подбор нормативно допустимых аналогов;
6. формирование отчёта.

Нажмите **Открыть отчёт**.

## Шаг 4. Проверьте отчёт и происхождение результата

В сводке проверьте контрольные значения:

| Показатель | Значение |
|---|---:|
| Всего | 24 |
| Точные | 8 |
| Вероятные | 8 |
| На проверку | 5 |
| Без совпадения | 3 |

1. Отфильтруйте таблицу по одной из категорий.
2. У позиции нажмите **Подробнее**.
3. Проверьте совпавшие признаки, различия, ответственность и ссылку на демонстрационное правило.
4. В блоке **Решение эксперта** можно выбрать другую ответственность и указать синтетическую причину длиной не менее 10 символов. Изменение создаёт новую версию результата и остаётся в аудите.
5. Вернитесь к отчёту и скачайте **JSON**, **Excel** или **PDF**. Экспорт учитывает последнюю сохранённую версию каждого позиционного результата.

Составной аналог можно увидеть у позиции `position-022`: компоненты основного плана совместно закрывают требуемое количество. Альтернативные планы считаются отдельно из тех же реально допустимых кандидатов и не расходуют общий ledger. Допустимость и распределение количества рассчитывает доменный код, а не LLM.

## Шаг 5. Задайте вопрос МТР-аналитику

1. Откройте **МТР-анализ** или [http://localhost:3000/mtr-analysis](http://localhost:3000/mtr-analysis). Тот же runtime доступен в глобальном виджете **МТР-агент**.
2. Выберите подсказку **Какой остаток материала SAP-DEMO-0001?** либо введите этот вопрос вручную.
3. Нажмите **Отправить**.

В пользовательском ответе должны появиться:

- текущий остаток `200 M`;
- уверенность;
- citations для SAP с кодом материала и датой snapshot;
- отметка экспертной проверки, если она требуется.

Названия инструментов, аргументы и технический JSON в диалоге не показываются. ADMIN видит редактированные операции `sap.getState`, `sap.getMaterialStock` и `llm.respond` на отдельном экране **Администрирование → Логи агента**.

Обновите страницу. Диалог и оба сообщения останутся: thread, сообщения, структурированный ответ и citations сохранены в БД.

Под ответом агента можно отправить один из девяти типов обратной связи, например
«Полезно», «Неверный факт» или «Не хватает источника». Отзыв сохраняется как
личный, изолированный по проекту кандидат в состоянии `QUARANTINED`. Он не меняет
ответы агента автоматически: дальнейшее использование возможно только после
отдельной проверки, regression-кейса и явного продвижения уполномоченным куратором.

Для второй проверки задайте вопрос:

```text
Кто отвечает за позицию position-007?
```

Ответ должен ссылаться одновременно на актуальную позицию Appius и синтетическое демонстрационное правило. Если вывод требует специалиста, интерфейс покажет соответствующую метку.

## Шаг 6. Проверьте логи агента и аудит

Сначала откройте **Администрирование → Логи агента**. Найдите один correlation-запрос и раскройте карточки операций: там доступны длительность, число попыток, prompt/model metadata, citations и безопасная сводка результата без секретов.

Затем откройте **Администрирование → Аудит**. Найдите последние события:

- `SCENARIO_RUN_CREATED`;
- `SCENARIO_STEP_COMPLETED`;
- `agent.request.received`;
- `agent.tool.request` и `agent.tool.result`;
- `agent.response.completed`.

Журнал содержит безопасные детали и идентификаторы сущностей, но не токены, cookies, connection strings или содержимое system prompt.

## Шаг 7. Проверьте универсальный проектный чат

Для локальной ветки с migrations `0008`/`0009` включите:

```dotenv
MTR_AGENT_ORCHESTRATOR_ENABLED=true
MTR_AGENT_UNIVERSAL_CHAT_ENABLED=true
MTR_AGENT_ACTIONS_ENABLED=true
MTR_AGENT_LIVE_LLM_ENABLED=false
```

Последнее значение намеренно оставляет deterministic runtime primary для локальной демонстрации. Затем в том же чате задайте:

```text
Покажи активные проекты.
Какой остаток труб по выбранному проекту?
Что дозаказать?
Подбери замену для CAT-DEMO-PIP-0005 и отдельно оцени надёжность.
```

Ответ должен содержать отдельные facts/tables, четыре независимых показателя, citations и ограничения. Обновите страницу: публичная структурированная карточка должна сохраниться без внутренних capability/provider данных.

Для проверки импорта приложите синтетический XLSX/CSV без команды. Сначала появится preview распознанных строк. Публикация выполняется только после явной команды создать новую спецификацию или версию. Подробный сценарий приведён в [руководстве по вложениям](mtr-agent-attachments-import.md).

## Что вы проверили

Теперь у вас есть воспроизводимый сквозной результат:

- актуальные Appius-позиции и текущий SAP snapshot;
- сохранённый серверный запуск из шести шагов;
- 24 позиционных результата с объяснениями и аналогами;
- отчёт в UI и трёх форматах экспорта;
- persisted-диалог агента с итогом и citations, а также отдельный ADMIN-журнал фактических инструментов;
- universal project/material answer, который сохраняет структурированные факты после reload;
- specification preview/publish и proposal/confirm для разрешённого RBAC-действия;
- owner-only обратную связь, которая попадает в карантин и не включает онлайн-обучение;
- аудит операций.
